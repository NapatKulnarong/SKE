## 0. The Spine

```
asset → system model → threat → risk → treatment → requirement → control → implementation → verification
                                    ↖___________ residual risk loops back ___________↙
```

| Stage | Lecture | Question it answers |
| --- | --- | --- |
| Asset & objective | L1, L5 | What are we protecting, and which CIA pillar? |
| System model (DFD) | L6 | What are we working on? |
| Threat | L6 | What could go wrong? |
| Risk | L3.1, L5 | How much does it matter? (Likelihood × Exposure) |
| Treatment | L6 | Mitigate, accept, transfer, or avoid |
| Requirement | L3.2, L6 | What must be true (and testably so)? |
| Control / design | L7 | Prevent, bound, recover |
| Implementation | L3.1 | Secure coding |
| Verification | L3.2, L6 | Did we do a good job? |

🔑 **Three recurring truths:** security is *built in, not bolted on*; **prevention never reaches zero**, so bound the damage; and **a finding is evidence, not a risk decision**.

## 1. Principles of Information Security (L1)

### CIA triad

![[cia_triangle.svg|420]]

| Pillar | Protects against | Mechanisms |
| --- | --- | --- |
| **Confidentiality** | Unauthorized use and **disclosure** | Encryption, access control |
| **Integrity** | Unauthorized **modification** | Hashing, checksums, digital signatures |
| **Availability** | **DoS** / disruption | BCP, HA, DR |

- **Integrity depends on confidentiality**: you can't prove data is unchanged if you can't control who reaches it.
- But integrity *can* break without a confidentiality breach: **accidental deletion by a legitimate user**, or **indiscriminate damage** aimed at disruption rather than theft.

### AAA services

![[aaa.png|320]]

- The three **A**s: **Authentication, Authorization, Accounting**. The lecture splits Accounting into **Auditing** (logs) + **Accountability** (who answers for it).
- **Identity** and **non-repudiation** are related but are *not* letters in the name.
- **Order:** identity → authenticate → authorize → audit → accountability.

| Concept | Meaning | Example |
| --- | --- | --- |
| Identity | You **claim** who you are | Username |
| Authentication | System **proves** the claim | Password, MFA, biometrics |
| Authorization | System decides **what you may do** | RBAC, ACLs, file permissions |
| Auditing | System **tracks what you did** | Logs, audit trails |
| Accountability | Someone is **held responsible** | Compliance records |
| Non-repudiation | You **can't deny** it | Digital signatures |

### Protection mechanisms (don't mix these up)

![[layering_cheese.png|340]]

| Mechanism | What it does |
| --- | --- |
| **Layering / defense in depth** | Multiple **overlapping** controls, so one gap doesn't expose everything |
| **Abstraction** | Assigns **classes and roles** to simplify permission management |
| **Data hiding** | Don't expose internal state beyond what the app/API needs. **Not** security by obscurity |
| **Encryption** | Supports C and I |

- **Defense in depth, outside in:** perimeter/network → endpoint/application → data. Wrapped by **policy management** and **monitoring & response**.
- **Longer layer list:** Governance → Physical → Network → Identity → Detection & Response → Infrastructure → Application → Data.

### Security principles + access models

- **Least privilege** ladder (least → most): Contractor → Sr. Support Tech → IT Manager → FTE.
- **MFA:** more than one proof of identity.
- **RBAC** = permissions by **role**. **ABAC** = permissions by **attribute** (user, resource, time, location).

### Two illustrative vulnerabilities

- **SQL injection:** unsanitized input **alters query logic**. `'; DROP TABLE users; --` breaks out of the string.
- **Careless command execution:** `rm -rf "C:\My Awesome Game` with a missing quote, or an app installed at `C:\`, means an uninstaller wipes the drive. Lesson: **destructive operations need scoping and validation**, not intuition.

## 2. Laws Relevant to Information Security (L2)

### Hierarchy of law (Thailand) — higher always overrides lower

| Level | Law |
| --- | --- |
| 1 | **Constitution** (supreme) |
| 2 | Constitutional Act · **Act** · Emergency Decree |
| 3 | Decree |
| 4 | Ministerial Regulation · Code of Law |
| 5 | Local / subordinate laws |

- **Constitutional Act extends the Constitution but cannot override it** (unlike US Amendments).
- **Palace Law sits outside the hierarchy** (royal succession, not public law).

### Criminal vs commerce (civil) law

| | Criminal | Commerce (civil) |
| --- | --- | --- |
| Purpose | Peacekeeping, social order | Contracts, commerce, inheritance |
| Enforcement | **Punishment** | **Rulings and judgments** |
| Parties | **Prosecutor** vs defendant | **Plaintiff** vs defendant |
| Interpretation | By the **letter** of the law | By the **intention** behind it |
| For engineers | Computer crime, some privacy fines | Contracts, IP |

### GDPR · PDPA · APPI

| | **GDPR** (EU) | **PDPA** (Thailand) | **APPI** (Japan) |
| --- | --- | --- | --- |
| Applies to | EU data subjects **anywhere in the world** | Anyone **physically in Thailand** | — |
| State actors | Covered | Some exemptions | — |
| Minimum age | **16** (lowerable to 13) | **10** | — |
| Pseudonymized data | **Defined** | Same core defs as GDPR | **Not defined** |
| DPO | Required | — | **No explicit requirement** |
| Portability / erasure | Strong | Ss. 31 / 33 | **Weaker, less defined** |

- **GDPR follows the data subject; PDPA follows presence in Thailand.**
- **APPI defines** *anonymized* and *retained personal* data, but **not pseudonymized**.

**GDPR rights:** Art. **13–14** information · **15** access · **16** rectification · **17** erasure ("be forgotten") · **18** restrict processing · **20** portability · **21** object · **22** automated decision-making. Plus **7** withdraw consent · **77** complaint · **79** judicial remedy · **82** compensation.

**GDPR Art. 4 terms:** personal data · processing (anything done to data) · consent (**freely given, specific, informed, unambiguous**) · **controller** (decides why and how) · **processor** (acts for the controller) · **DPO**.

**PDPA sections:** **26** bans collecting sensitive data without consent (race, ethnicity, political opinion, disability, union membership, genetic/biometric) · **30** access · **31** portability · **32** object · **33** deletion/anonymization · **34** stop use · **35** rectification · **19(5)** withdraw consent · **73** complaint.

### Computer Crimes Act (2550/2007, amended 2560/2017)

| S. | Offense |
| --- | --- |
| 5 | Unauthorized access to a **system** |
| 6 | Exposing security/defense mechanisms |
| 7 | Unauthorized access to **data** |
| 8 | Wiretapping / eavesdropping |
| 9 | Unauthorized destruction or alteration of data |
| 10 | Disrupting computer systems |
| 11 | Concealing the source of data/email |
| 12 | Distributing malware |
| **14** | **Spreading false information** (very frequently invoked) |
| 16 | Defamation via false info, including **deepfakes** |

⚠️ **S.14 problems:** used for defamation claims, "false information" is vaguely defined, and it overlaps other laws. **S.15 also punishes platforms that "allow" S.14 violations** (unclear safe harbour). Note: computer crime law generally **does not cross borders**, unlike privacy law.

### Cybersecurity Act (2562/2019)

Creates the **NCSC**, defines **critical information infrastructure** (national security, government services, banking, telecom, transport/logistics, energy/utilities, health, plus NCSC designations), and sets emergency response measures.

### Intellectual property + licences

Default: **all rights reserved** unless permission is granted.

| IP type | Protects | Note |
| --- | --- | --- |
| **Copyright** | Creative work | **Automatic, no registration.** Pushing to GitHub counts as publication |
| **Patent** | Inventions/designs | Software patents exist but are **rare** |
| **Trademark** | Brand marks/names | — |
| **Trade secret** | Confidential business info | Covers espionage, **not clean-room reverse engineering** |

- **GPL (copyleft):** build with it and your **entire project** must be GPL. It "infects."
- **LGPL:** merely *using* the library leaves your project free; **only forks of the library itself** stay LGPL.
- **Creative Commons Share-Alike** is the content analogue, **looser** than copyleft.

### Reidentification risk + dark patterns

- "Anonymized" or aggregated data can be traced back by **cross-referencing datasets** (voter list + record index + ballot table reveals votes).
- **Small groups leak**: "3 of 5 students at risk" identifies people.
- 🔑 **Anonymization is not automatically privacy-safe.**
- **Dark patterns** = manipulative UI that tricks users, often specifically to extract PII. Links UX choices directly to privacy law violations.

## 3. Standards, SSDLC & Secure Coding (L3.1 + L3.2)

### SSDLC — a security activity on every stage

![[SSDLC.png|460]]

| SDLC stage | Security activity added |
| --- | --- |
| Planning & Requirements | Risk assessment, security requirements |
| Design | **Threat modeling** |
| Implement | Secure coding, code scanning |
| Test | Code test, security test, pentest |
| Deployment | Hardening |
| Maintenance & Support | Patching, monitoring, incident response |

- 💰 Fixing a vulnerability at **design costs 30–60× less** than in production (NIST / IBM / Gartner).
- **The SDLC is a loop, not a line.** Findings at any stage can send you back. Be flexible.

### Risk = Likelihood × Exposure

![[risk_table.png|420]]

- **Likelihood** = how likely is someone to actually attack this? **Exposure** = how much damage if it succeeds.

| Likelihood factors | Exposure factors |
| --- | --- |
| **Industry risk** (high: banking, fintech, health) | Downtime / SLA violations |
| Known **incident rate** | **Legal liability** (HIPAA, GDPR fines) |
| Risk of **internal mistake** | **Reputational** damage, customer loss |
| Risk of **opportunistic attack** | Financial damages |
| Stack **popularity** (popular = more exploited) | Harm to employee **health/life**, incl. psychological |

- Scoring is a **coarse judgement (low/med/high), not a calculation**.
- **NIOSH example:** more complex models can combine several factors when a 2-variable matrix is too crude.
- **Convenience vs security:** a system with no connections and no functionality is perfectly secure and useless. **Every feature expands what needs protecting.**

### Threat modeling in design — the 4 steps

![[threat_modeling_four_steps.svg|480]]

| Step | Meaning |
| --- | --- |
| **Decompose** | Map data flows, trust boundaries, entry points, sensitive data |
| **Categorize** | Classify threats per part (**STRIDE**) |
| **Rank** | Score by likelihood × exposure |
| **Mitigate** | Assign a control per threat (prevent, reduce, limit) |

**Output:** security **technical specifications** + a **security test plan**.

### Design before code

![[isms_to_secure_coding_flow.svg|480]]

**ISMS** sets policy and risk posture → **Secure Design** turns it into architecture (data flows, trust boundaries) → **Secure Coding** implements it.

| Core design principle | Meaning |
| --- | --- |
| Least privilege | Only the permissions needed |
| Defense in depth | Multiple independent controls |
| **Secure by default** | Default state should be safe |
| Minimize attack surface | Remove unnecessary interfaces/features |
| Trust boundaries | Treat lower-trust input cautiously |
| Fail securely | Failure must never accidentally grant access |

| Design decision | Coding implementation |
| --- | --- |
| Role-based access model | **Server-side** authorization checks |
| Untrusted input boundary | Validation + parameterized queries |
| Sensitive-data requirement | TLS + hashing + secret management |
| Limited component privileges | Restricted service/DB accounts |
| Secure session design | Secure cookies, token rotation, logout |
| Safe failure behavior | Generic errors, protected logs |

### Secure coding, five areas

![[bug_to_impact_escalation.svg|480]]

**Bug → Vulnerability → Exploit → Impact.**

1. **Validate input & prevent injection** — validate **server-side** (type, length, range, format), prefer **allowlists**, keep **data separate from commands** (parameterized queries). Stops SQLi, XSS, command injection.
2. **AuthN / AuthZ / least privilege** — who are you / what can you do / how much access do you need. ⚠️ **Hiding a UI button is not authorization.**
3. **Protect sensitive data** — TLS in transit, **hash + salt** passwords, secret management, **trusted crypto libraries** (never roll your own). Watch for *outdated* hashing, not just missing.
4. **Sessions, errors, logging** — unpredictable IDs, **regenerate after login**, timeouts; generic error messages, no stack traces; log security events, protect logs, **never log secrets**. Never expose session tokens, passwords, API keys, DB details.
5. **Dependencies & config** — risk is inherited: app code → libraries → runtime/server → configuration.

**Developer checklist:** input · queries · access · privilege · secrets · errors · dependencies · review. *Secure coding is a repeated habit, not a one-time checklist. Tools assist reasoning; they don't replace it.*

### SAST vs DAST

| | **Static (SAST / SCA)** | **Dynamic (DAST)** |
| --- | --- | --- |
| Scans | **Source code**, before compile or run | The **running** application at its interface |
| Cadence | Required **checkpoint** before code leaves the SDLC; wired into the build | **Multiple times per iteration**, supports 24/7 |
| Ties into | Build process, QA readiness | **Incident response** |

### Microsoft SDL — 12 practices

Training · Define security requirements · Metrics & compliance reporting · **Threat modeling** · Design requirements · **Cryptography standards** (vetted, swappable) · Third-party component risk (inventory + patch plan) · Approved tools · **SAST** · **DAST** · **Pen test** · **Incident response**.

### Where requirements come from

**A. Standards, laws, regulations:** GDPR, PDPA, HIPAA · ISO/IEC 27000-series · NIST SP 800 · OWASP ASVS · PCI.

**B. Business/product**, split into:

| Positive (functional, what it **must** do) | Negative (risk-driven, what it **must not** do) |
| --- | --- |
| Lock account after 6 failed logins | Data must not be altered/destroyed by unauthorized parties |
| Passwords ≥ 10 alphanumeric chars | App must not be usable for unauthorized financial transactions |
| Mask confidential fields on screen | *(harder to test — no defined expected behavior)* |

### The standards themselves

| Family | Key facts |
| --- | --- |
| **ISO/IEC 27000-series** | A **management system** standard, not a tech spec. **27000** vocabulary · **27001** ISMS requirements (**the certifiable one**) · **27002** controls · **27003** implementation guidance. Requires: identify risks → design & implement controls → maintain, with evidence |
| **NIST SP 800** | US NIST. **SP 800-53** = Security & Privacy Controls |
| **OWASP** | Non-profit, **application** security. Top 10 · **ASVS** (web) · **MASVS** (mobile) · Testing Guide · WebGoat |
| **PCI** | Founded **2006** by Amex, Discover, JCB, MasterCard, Visa. **PCI DSS** (12 requirement areas), PA-DSS, Secure Software Standard |

**ASVS serves as** a **metric** (how trustworthy is this app?), **guidance** (how do I build it?), and a **procurement basis** (what do I demand from a vendor?).

| ASVS level | For | Verification style |
| --- | --- | --- |
| **1** | Low assurance | Fully pen-testable, **black-box**, no source needed |
| **2** | Sensitive data (**recommended default**) | Secure coding, architecture review, SAST/hybrid, unit tests |
| **3** | High-value transactions, sensitive medical | Same as L2 at **highest rigor** |

**ISO 27001 ↔ OWASP mapping:** A.9 Access Control ↔ ASVS/Cheat Sheets · A.12.6 Vulnerability Mgmt ↔ Top 10, Dependency-Check · A.14 Secure Development ↔ SAMM, ASVS, Threat Modeling · A.12 Logging ↔ ASVS V10 · A.18 Compliance ↔ Privacy by Design.

🔑 **The three-step takeaway:** **select** the standards that apply → **read** what they actually require → **choose controls based on real risk**, not compliance theater.

## 4. Cryptography & PKI (L4)

![[cryptography.png|300]]

**Cryptography** = a mathematical method to transform data so unauthorized people can't read or modify it. It prevents **eavesdropping** (secret reading), **tampering** (unauthorized alteration), and **falsification** (presenting fake data as genuine).

🔑 **Crypto serves C and I, never A.**

### Classical ciphers

| Cipher | How | Key | Note |
| --- | --- | --- | --- |
| **Substitution** | Swap each letter via a table | Fixed table | Monoalphabetic |
| **Caesar** | Shift by a fixed number | A number | **ROT13** = key 13, **self-inverse** |
| **Vigenère** | Shift by a **repeating keyword** | A word | **Polyalphabetic**, much harder |

All three are alphabetic; **modern crypto works on bits and bytes**.

### Symmetric — one shared key for E and D

| | **Block** | **Stream** |
| --- | --- | --- |
| Examples | **DES†, AES** | **RC4** |
| Operates on | Fixed-size blocks | Continuous bit/byte stream |
| Key concepts | Key schedule, subkeys, rounds | Keystream, initialization vector |
| Used in | AES → HTTPS, IPSec, disk encryption | RC4 → legacy TLS/VPN |
| Trade-off | **Higher security** | **Faster**, good for real-time |

- **DES:** **Feistel network**, data split 50:50, **16 rounds** of `F`, same circuit both ways (reverse key order). **Broken — 56-bit key is brute-forceable.** († 3DES disallowed by NIST from 2023.)
- **AES:** **128/192/256-bit**, processes the **whole block** each round. Round = **SubBytes → ShiftRows → MixColumns → AddRoundKey**.
- **RC4:** **KSA** (builds scrambled 256-byte state) + **PRGA** (streams keystream bytes to XOR).
- **Pros:** simple, fast, good enough. **Cons:** key leak exposes everything, and **key exchange is the hard part**.

**Diffie-Hellman (1976)** solves key exchange: each side combines its own private key with the other's public key to reach the **same shared secret without ever transmitting it**. Paint-mixing analogy.

![[dh_color_buckets.png|260]]

### Asymmetric — linked public/private keypair

![[asymmetric_key.png|460]]

Encrypt with **Bob's public** key; only **Bob's private** key undoes it. Deriving private from public must be computationally infeasible.

| | **RSA** | **ECC** |
| --- | --- | --- |
| Hard problem | **Factoring** a product of two large primes | **Elliptic curve discrete logarithm** |
| Curve | — | `y² = x³ + ax + b`, discretized mod a large prime |
| Secure key size | **2048 / 3072 / 4096-bit** | **256-bit** (≈ 3072-bit RSA) |
| Speed | Heavier | **Lighter**, good for mobile/IoT |
| Quantum | **Vulnerable** (Shor's algorithm targets factoring) | Generally better, not immune forever |

**RSA mechanics:** pick primes `p, q` → `n = p × q` → derive `e` and `d` via Euler's totient. **Public = (n, e)**, **private = (n, d)**. Encrypt `c = m^e mod n`, decrypt `m = c^d mod n`. Security rests entirely on **factoring `n` being infeasible**; whoever factors `n` reconstructs `d`.

**Pros:** great for sending to a specific person, strong. **Cons:** expensive, complex in hardware. Commonly used **to set up a faster symmetric session**.

### Digital signatures

![[digital_signatures.png|460]]

- **Sign with your PRIVATE key → verify with your PUBLIC key.** (The reverse of encryption direction.)
- Goal is **authenticity + integrity**, **not confidentiality**. Signing ≠ encryption.
- Legally recognized (Japan's Electronic Signature Act, US ESIGN Act); used for release signing, commit signing.
- ⚠️ **Critical caveat:** a signature proves only *"whoever holds this private key signed this"* — **not** that the key belongs to the claimed person. **That is exactly what PKI solves.**

### PKI

**Problem:** how do you know a public key really belongs to who it claims?

**Solution:** **Certificate Authorities** verify identity and issue **certificates** binding a public key to a verified identity.

- **Chain of trust:** **Root CA** (self-signed, pre-trusted by OS/browser) → **Subordinate CA** (trusted *because* the root vouches) → individual certificates.
- **Revocation:** if a private key is compromised, the CA revokes the cert; anything signed after that date is untrustworthy.
- **Before trusting a root CA, verify it is:** **Valid · Authentic · Trustworthy · Purposeful.**
- **Future:** blockchain-based PKI (zero-trust, faster, cheaper than CA fees). **Quantum** will probably break RSA *eventually*, but it is **not an immediate threat** (noisy qubits, few players, bigger priorities).

## 5. Risk Assessment Workshop (L5)

**Setup:** 20,000 secondary students across 77 schools on Planet Astra; the provincial education committee wants **mental health data** via the **PHQ-A** (9 items `Q1`–`Q9`, each scored **0–3**; the last asks about **self-harm**). This is **health data about minors**, the most sensitive combination possible.

### The central conflict (a requirements-phase finding)

| Goal | Needs | Privacy cost |
| --- | --- | --- |
| **Survey** ("5,000 of 20,000 at risk") | Aggregate statistics only | **Low** |
| **Intervention** ("help this child") | Identify specific students | **High** |

⚠️ **Conflicting requirements are a security finding.** They can't be resolved by "do both" — **separate, scope, or escalate**. Found now it's a conversation; found after the database is built it's a redesign.

### The schema is a policy document

Naive table = `UUID, First Name, Last Name, School, Grade, Q1..Q9`. Why that single table *is* the risk:

- **Direct identification** — name + school + grade identifies a child instantly.
- **Sensitive by association** — joined to Q1–Q9 it becomes a **diagnosable mental-health profile of a named minor**.
- **One breach = total loss** — no partial failure mode.
- **Legal exposure** — sensitive personal data (**PDPA Art. 26 / GDPR Art. 9**).
- **Over-collection** — the survey goal needs *none* of the PII. Violates **data minimization** before any attacker appears.

### Stakeholders

![[research_project_org_chart.svg|520]]

- **Students** are the data subjects, **furthest from every decision**, with no institutional power.
- **Infrastructure belongs to a third party** (another university's Google Workspace): whoever owns the account owns the logs, admin console, and effectively the data.
- **Teachers** collect answers *and* see students daily — a **coercion channel and a confidentiality leak at once**.

### Consent

**You must know first:** age of the subject · jurisdiction · what data (sufficient *and* minimal, **nothing "just in case"**) · purpose (**consent is purpose-bound**; new purpose = new consent) · retention period (**a stated number, not "indefinitely"**).

🔑 **A consent form can't be written until the design is settled**, because it must describe the design accurately. An unclear design produces an unlawful form.

| | Legally | Ethically |
| --- | --- | --- |
| Who consents | **Parents**, on the child's behalf | The child must also **assent** |
| Age | **PDPA 10 · GDPR 16** (→13) | Capacity to understand beats the number |
| Participation | Parents may legally *send* a child | **Being sent ≠ being willing** |

❤️ **Legal sufficiency ≠ ethical sufficiency.** Parental consent authorizes the *research*; it doesn't make the child a willing participant. On a mental-health instrument, **the child's cooperation IS the data source**.

**Coercion traps:** "it's for science", "it'll help others", "they get a gift card", "parents consented". These persuade **adults, not children**; **inducements make refusal costly, so consent is no longer freely given**.

🔑 **Ethics and data quality point the same way.** Coerced students mark randomly, answer defensively, or hide symptoms (especially Q9). You get a dataset that is both unethical **and wrong**. Coercion doesn't buy coverage; it buys undetectable noise.

### The "kidnap for random sampling" thought experiment

| Part | Claim | Verdict |
| --- | --- | --- |
| **True premise** | Consent causes self-selection bias | ✅ Genuinely true |
| **Smuggled step** | So a *methodological* need outweighs a *rights* constraint | ❌ **The actual error, never stated aloud** |
| **Absurd conclusion** | So kidnapping is justified | ❌ Obviously wrong |

- The cartoon ending is the **teaching device**: the same move sounds professional as *"we need real usage data, so let's not tell users we're logging it."*
- It **fails on its own terms**: bias has legitimate remedies (report response rates, weight/stratify, IRB waiver for low-risk studies, aggregate-only collection). Coercion just swaps *selection* bias for *response* bias, which is **harder to detect**.
- 🔑 **Be suspicious of any argument shaped "good research requires skipping a safeguard."** An AI will argue **either side** fluently; its refusals track how obviously bad the example looks, not the principle. **It cannot supply your ethical floor.**

### Pseudonymization and its limits

![[pivot_table.png|520]]

- **Pseudonymization** = identifiers replaced with a code **while the mapping still exists**. Still **reversible**, and it must be, because individual follow-up requires re-identification by design.
- ⚠️ **Pseudonymized ≠ anonymized.** Under GDPR pseudonymized data is **still personal data**, fully regulated. Only **irreversible anonymization** leaves the law's scope, which is incompatible with individual follow-up.

**Hunt the Witch (targeted re-identification):** you know the target's **grade, gender, and school** (collection is school by school). Filtering on those three often leaves **one row**. Nothing was broken into; the quasi-identifiers you kept "for analysis" did the work.

🔑 **Aggregation doesn't save you when the group is small. Small cells leak.**

**Linkage attack:** join a leaked voter list (`Name, ID, Gender, Zip`) to a public "anonymized" insurance set (`Gender, Zip, Disease`) on **Gender + Zip**. One male in zip 10800 → **named individual + diagnosis**.

```
Public "anonymous" health data  +  Obtainable identity list
        └──── join on quasi-identifiers ────┘
                          ↓
         Named individual + medical diagnosis
```

- **Quasi-identifiers** identify nobody alone but almost everybody in combination: gender, zip, birth date, school, grade.
- The attacker **needs no access to your system**; they attack the *published* version.
- **Defenses:** suppress small cells · coarsen values (grade band, region) · enforce minimum group size (**k-anonymity**) · don't release row-level data.

### Organizational risks (no technical fix, and these produce the fines)

- **Jurisdiction:** targeting people in the EU brings **GDPR** regardless of where you are. **Cross-border transfer is its own regulated act** — here the Workspace account belongs to another university, so data lands in another country under another regime, reachable by an admin who never signed your consent form. **Two regimes may apply at once, and the strictest governs.**

| Role | Meaning | In this project |
| --- | --- | --- |
| **Data Controller** | Decides **why** and **how** | Research Committee |
| **DPO** | Oversees compliance, contact for regulators | The committee university's DPO |
| **Data Collector** | Obtains data from the subject (*functional*, not a formal legal role) | Teacher |
| **Data Processor** | Processes **on the controller's instructions** | *unassigned* |
| **Data Recipient** | Receives disclosed data | *unassigned* |

**Why ambiguity is itself a risk:** an **accountability gap** (nobody answers access/rectification/erasure requests, which have statutory deadlines) · **liability surprise** (roles follow **what you actually do**, not your title — "I was just the advisor" is no defence if you set the purpose and schema) · **Google as unmanaged processor** with no data processing agreement.

### The assessment, and the architectural answer

| Risk | L | E | Mitigation |
| --- | --- | --- | --- |
| PII + PHQ-A in one table leaks | M | **H** | Split tables, pseudonymize, restrict the mapping |
| Re-identification via quasi-identifiers | **H** | **H** | Coarsen fields, suppress small cells, no row-level publishing |
| Invalid consent (coerced child, parent-only form) | **H** | M | Parental consent **+ child assent**, real right to decline |
| Data quality collapse from coercion | **H** | M | Voluntary participation, report response rates |
| Cross-border transfer via third-party Workspace | M | M | Data processing agreement, deliberate hosting |
| Unassigned controller / processor roles | **H** | M | Assign roles **in writing before collection** |
| Scope creep from survey into tracking | **H** | **H** | Two goals → two datasets → two consents |

🔑 **Don't build one system that does both. Split it:** an **aggregate dataset** (genuinely anonymized, safe to publish) and an **intervention pathway** (separate, tightly controlled, own consent, access control, retention limit). **Re-identification becomes an act, not a property** — deliberate, authorized, and logged.

## 6. Threat Modeling (L6)

![[security_existed_before_app.svg|480]]

🔑 **The objective predates the software.** Moving a paper form into a database changes the threats, probabilities, and available controls, but **not what you owe the person**.

### Threat modeling vs risk assessment

| | **Threat modeling** | **Risk assessment** |
| --- | --- | --- |
| Does | Discover and describe credible failures | Evaluate **significance in context** |
| Asks | **What could go wrong?** | **How much does it matter?** |
| Model | Actors, flows, boundaries, misuse cases | **Probability × Exposure → Risk** |
| Output | Threat/abuse scenarios + candidate mitigations | Prioritization + a **treatment decision** |

- **TM enumerates, RA prioritizes.** Generate freely, *then* filter — filtering early loses threats you can't yet fix.
- Threat scenarios aren't the only input: **scanner findings and organizational risks get scored the same way**.

### Threats aren't only attackers

![[threat_sources.svg|480]]

Mistaken users, compromised insiders, and **plain system failure** (an expired dependency) break objectives with **no malice involved**, and **authentication stops none of them** — insiders already hold valid credentials.

### Model the system first

![[threat_model_dfd.svg|480]]

**DFD elements:** actors · components · data flows · data stores · entry points · **trust boundaries**.

🔑 **The diagram's value is the boundaries, not the boxes.** OWASP's question 1 covers system, users, dependencies, **assumptions**, and trust boundaries — the last two are what people skip, and **unwritten assumptions are where threats hide**.

**CWE-501 trust boundary violation:** a boundary is a line where data goes from **untrusted to trusted**; **validation logic is what lets data cross safely**. The violation is **mixing trusted and untrusted data in one structure**.

1. **Validation is the gate, not decoration.** If you can't point to where the check happens, the data isn't trusted; you're hoping.
2. A session holding a **server-derived user ID *and* a client-supplied role** invites reading the wrong field. **The violation is at design level, before any exploit exists.**

*Real-world boundaries:* airport checkpoint, immigration counter, bank teller window.

### The Four Question Framework

![[stride_prompts.svg|480]]

| # | Question | Produces |
| --- | --- | --- |
| 1 | What are we working on? | The system model |
| 2 | What can go wrong? | Threat and abuse scenarios |
| 3 | What are we going to do about it? | **Treatment decisions and requirements** |
| 4 | Did we do a good job? | Verification, review of decisions, **residual risk** |

⚠️ **STRIDE is a prompting technique for question 2, not the definition of threat modeling.** Teams that start with STRIDE produce a categorized list of threats for a system nobody described and no decision anybody made.

### From threat to testable requirement

![[threat_to_requirement.svg|480]]

- A requirement **states what must be true**, can **fail a test**, and doesn't name a library (so the design stays free).
- 🔑 **Name both the principal and the object.** "The caller is authenticated" is not enough — the bug is checking the *principal* but never that the *object belongs to them*.
- Pair every requirement with a **negative test that can fail**.

### Design to prevent, bound, recover

- **Prevention never reaches zero**, so bound the **blast radius** of the failure you know is coming.
- An export capped at 50 rows instead of 20,000 turns a breach into an incident.
- Each defense-in-depth layer must be an **independent** control, not a retry of the previous one.

### Destructive operations

![[delete_confirm_flow.svg|480]]

- 🔑 **Authorization is not intent.** "Are you allowed?" leaves open "did you mean this?"
- ⚠️ **`LIMIT 1` is a guardrail, not proof the right row was selected.** If the invariant is "exactly one object," matching **zero or two rows must abort**, not silently delete the first.
- **Bound the damage of a correct-looking-but-wrong action, and make the scope visible before it's irreversible.** Never rely on "the operator will be careful."

![[friction_by_severity.svg|420]]

**Strategic friction** should be **proportional to severity**. An OTP can be authentication, reauthentication, transaction authorization, or plain friction — **always name which property a control provides**.

### Verification is not "run a scanner"

| Mechanism | The question it answers |
| --- | --- |
| **Review** | Does the design/code implement the **intended requirement**? |
| **SAST** | What **suspicious code patterns** can static analysis find? |
| **SCA** | What **known dependency/component risks** are present? |
| **DAST** | What issues are **observable through a running interface**? |
| **Security tests** | Do **specific security requirements** hold? |
| **Pen test** | What **attack paths** can skilled adversarial testing uncover? |

🔑 **Only 2 of 6 can confirm your requirement was met: review and security tests.** Scanners find *classes of defect*; they have no idea what your system was supposed to guarantee.

**Finding ≠ Vulnerability ≠ Scenario ≠ Risk.** A "critical" in unreachable code may be noise; a "medium" on the endpoint holding sensitive data may be top priority. ⚠️ **A scanner severity is evidence, not your business risk decision.**

**Triage:** ① validate the finding → ② understand exploit conditions and affected assets → ③ assess probability and exposure **in context** → ④ **treat, accept, escalate, or redesign** → ⑤ reassess **residual risk**. *"Accept" is a legitimate documented decision; silence is not.*

### Capstone: produce the reasoning, not a list of bugs

① assets & objectives → ② DFD / trust boundaries → ③ threat scenarios (STRIDE as prompts) → ④ **probability × exposure** → ⑤ **treatment decisions: mitigate, accept, transfer, or avoid** → ⑥ testable requirements → ⑦ controls: **prevent / bound / recover** → ⑧ **verification plan**.

✅ **Success criterion:** *another team should be able to implement and test your requirements without guessing what "secure" means.* If your output is a list of scary words, it fails.

## 7. Software Security Design (L7)

### Secure design principles

| CISSP | US-CERT |
| --- | --- |
| Fail securely · Defense in depth · Least privilege · Separation of duties · Privacy by design · Zero trust · Keep it simple · Trust but verify · Secure defaults | Failing securely · Defense in depth · Least privilege · Separation of privilege · Promoting privacy · Reluctance to trust · Economy of mechanism · Least common mechanism · Never assuming your secrets are safe · Complete mediation · Psychological acceptability · Securing the weakest link |

**Secure defaults** — whatever ships out of the box **is** the real security posture, because most users change nothing. Defaults are picked to **minimize installation problems** and support load, so **easy setup serves the vendor, hardening serves you**. Deploying someone else's product? Assume defaults are the **worst** option and review **every** setting. Building your own? **Make secure the default.** Microsoft's **SDL** uses **SD3+C** = Secure by **Design, Default, Deployment and Communication**. Locked-down products **need good documentation**, or a frustrated admin disables protections wholesale.

**Fail securely** — failure management = **exception handling** (programmatic errors) + **input validation/sanitization/filtering** (bad input). Fail **closed**, show a **generic error and log details privately**, **leave a safe state** (no half-finished actions or leftover privileges).

**Keep it simple (KISS)** — the more complex, the harder to secure. **DRY** (write logic once, so a fix happens in one place) · **Rule of least power** (use the **least powerful language/tool** that still solves the problem, since less power means less to abuse) · **YAGNI** (every extra feature is **more attack surface**).

**Zero trust vs trust-but-verify**

| | Old (castle and moat) | **Zero trust** |
| --- | --- | --- |
| Assumption | Inside trusted, outside not | **Neither is trusted** |
| Access | Authenticate once, then generic internal access | **Every request authenticated, authorized, and encrypted** |

Broken by **mobiles, cloud, IoT, and insider breaches**. Tools: internal segmentation firewalls, **MFA**, **IAM**. 🔑 Design around zero trust; trust-but-verify is **no longer sufficient**.

**Privacy by design** — build privacy in at **early design**; **prevent** violations rather than remedy them.

**Least privilege** — only what the **current task** needs. **Default = no access**, elevate when needed, **drop rights when unused** (`sudo`, `su`, setuid).

**Separation of duties vs separation of privilege**

- **Duties:** no one person controls a critical function end to end, so breaking it takes **collusion**. Split admin and security powers. Don't make a job so big it needs too many permissions.
- **Privilege:** never grant on **one condition**; require **multiple independent checks**. `su` to root needs the **root password AND `wheel` membership**.

**Fail-safe defaults (deny by default)** — unless explicitly allowed, **deny**. **Justify why someone should have access, not why they shouldn't.** If an action fails, the system is **as secure as when it began**.

| Principle | Point |
| --- | --- |
| **Economy of mechanism** | Security mechanisms as **simple** as possible; keep interfaces between security modules simple |
| **Complete mediation** | Check **every** access to **every** object, including at **initialization, shutdown, and restart** |
| **Open design** | Security must **not** depend on secrecy of design. **Security through obscurity is bad**; a friend should find the bug before a foe |
| **Least common mechanism** | **Don't share** access mechanisms; every shared one is a **potential information path** |
| **Psychological acceptability** | Don't make it much harder to use, or people bypass it. **Don't leak extra info**: "user ID **or** password was wrong" |

### Subjects, objects, trust, system types

- **Subject** requests access; **object** is the resource. **Roles are per request, not permanent** (A asks B, then B asks C, so B is now a subject).
- **Transitive trust:** A trusts B, B trusts C, so A can **inherit trust of C and bypass a restriction** between A and C.

| | **Closed** | **Open** |
| --- | --- | --- |
| Built for | Narrow peers, often one vendor | Agreed industry standards |
| Standards | **Proprietary, often undisclosed** | Public |
| Integration | **Harder** with unlike systems | **Easier** across vendors |
| Security | **Can be** more secure | More vulnerable |

### Fail-secure vs fail-open

![[fail_terms_physical_digital.png|480]]

| Term | Digital | Physical |
| --- | --- | --- |
| **Fail-open** | Priority = **availability**; connection continues, maybe unfiltered | Emergency door **opens** (protects people) |
| **Fail-closed / fail-secure** | Priority = **C and I**; connection is **cut**. Memory-isolation violation → OS halts and reboots (**BSoD**) | Vault **locks** (protects assets) |
| **Fail-safe** | Same as **fail-closed** (protects C, I) | Door **opens** (protects people, like fail-open) |
| **Fail-soft** | **Keeps running** after a component dies (other apps survive one crash) | n/a |

⚠️ **Fail-safe flips meaning:** digital **cuts off**, physical **opens up**. **Fail-soft is about staying alive**, not about opening or closing.

### Techniques for ensuring CIA

![[confinement-flow.svg|560]]

**Chain:** **authority level → bounds → confinement → isolation.**

| Technique | Point |
| --- | --- |
| **Confinement** (sandboxing) | Restrict a program to specific locations/resources. **Least privilege applied to processes.** Stops data leaking |
| **Bounds** | Each process has an **authority level** (user vs kernel) setting which memory addresses and resources it may touch. **How confinement is enforced** |
| **Isolation** | Once bounds are enforced, the process **cannot touch another app's memory or resources** |
| **Access controls** | Subjects reach **only authorized objects** (read-only for most, read-write for a few) |
| **Trust vs assurance** | **Trust** = mechanisms are **present**, designed in. **Assurance** = how **reliable** they are in practice, **continually maintained and reverified** |

*Example:* MFA existing is **trust**; testing that it can't be bypassed, and rechecking after each update, is **assurance**.

### Security models

A model **maps abstract policy into algorithms and data structures** you can build, so designers can measure a design against it.

![[tcb-security-perimeter.svg|560]]

**TCB** = the hardware + software + controls you trust to enforce the policy; **everything outside gets no guarantee**. **Keep it small so it can be analyzed.**

- **Security perimeter** — the imaginary boundary around the TCB.
- **Trusted path** — the only allowed channel across that boundary.
- **Reference monitor** — **checks** every access before granting it.
- **Security kernel** — the TCB components that **implement** the reference monitor.

🔑 A request crosses the perimeter via the trusted path, the **reference monitor validates**, the **security kernel enforces**.

| Model | Core idea | Key rule | Protects |
| --- | --- | --- | --- |
| **TCB** | The small part you trust | Perimeter, trusted path, reference monitor, kernel | C, I, A (foundation) |
| **State machine** | Secure in **every state** | Every legal transition lands in a secure state | C, I, A (base for others) |
| **Information flow** | Built on state machine | Allow authorized flows, block unauthorized | C, I |
| **Take-Grant** | How **rights move**, so you see leaks | **Take, Grant, Create, Remove** | C, I |
| **Access control matrix** | Who can do what to which object | **ACL** = column (per object), **capability list** = row (per subject) | C, I |
| **Bell–LaPadula** | Stop secrets leaking **down** | **No read up, no write down** | **C only** |
| **Biba** | Keep trusted data uncontaminated | **No read down, no write up** | **I only** |
| **Clark–Wilson** | Change data only via trusted programs | **Subject → program → object**; well-formed transactions; separation of duties | **I** |
| **Brewer–Nash** (Chinese Wall) | Access changes with **what you've seen** | Wall around the rest of a conflict-of-interest class | **C** (conflict of interest) |

![[take-grant-model.svg|520]]

**Take-Grant:** **Grant = push** your rights out; **Take = pull** rights in. If X has `t` on Y and Y has `r,w` on Z, then **X can take `r` on Z**.

![[bell-lapadula.svg|480]]

**Bell–LaPadula** — US DoD, 1970s, classified info. **Simple Security = no read up. Star (*) / Confinement = no write down. Discretionary Security** adds an access matrix for DAC. Read **down** is fine; write **up** is fine. **Quick check: "who can read this afterward?"** Copying a Classified paragraph into a Sensitive file is a **write-down violation**.

![[biba.svg|480]]

**Biba** — same lattice, flipped for **integrity**. **No read down** (don't ingest less-trusted data; air-purity analogy) and **no write up** (a low-integrity subject must not corrupt a high-integrity file, e.g. a web form must not overwrite payroll). **Three goals:** stop unauthorized modification, stop **authorized subjects making unauthorized** modifications, protect internal and external consistency.

![[clark-wilson.svg|420]]

**Clark–Wilson** — commercial, no classification levels. **Subjects never touch objects directly**: client → interface/portal → database. A teller uses the banking app, which validates every transfer.

⚠️ **Availability is only covered by the broad foundations (TCB, state machine). No specific model targets it, and Bell–LaPadula explicitly ignores it.**
**Quick memory:** Bell–LaPadula and Brewer–Nash = **confidentiality**; Biba and Clark–Wilson = **integrity**.

### Security capabilities of information systems

| Capability | Role |
| --- | --- |
| **Memory protection** | A process **cannot touch memory not allocated to it, regardless of which programs are running** |
| **Virtualization** | Host multiple OSs in one machine's memory; also a security tool (isolate OSs, test suspicious software) |
| **TPM** | Cryptoprocessor on the mainboard storing/processing keys for **hardware disk encryption**, treated as **more secure than software-only** |
| **Constrained interfaces** | What a user can **do or see** depends on privilege (hidden or **dimmed** menus). Limits **authorized and unauthorized** users |
| **Fault tolerance** | Suffer a fault and **keep operating** (RAID, failover clusters). Avoids single points of failure |
| **Encryption** | Plaintext ↔ ciphertext, supporting C and I |

## 9. High-Yield Confusions

> [!warning] This is where marks are lost
> Every row is a pair the lectures deliberately place near each other.

| Pair | The distinction |
| --- | --- |
| **Secure defaults** vs **fail-safe defaults** | Shipped **configuration** vs **denying** what isn't explicitly permitted |
| **Economy of mechanism** vs **rule of least power** | Reduce **complexity** of the security mechanism vs reduce **capability** of the tool you pick |
| **Separation of duties** vs **separation of privilege** | No one **person** controls it end to end (needs collusion) vs no **single condition** grants it (needs multiple checks) |
| **Layering** vs **abstraction** | Stacks defenses vs groups entities into classes/roles |
| **Data hiding** vs **security by obscurity** | Don't expose internal state (good) vs rely on secrecy for security (bad, see open design) |
| **Fail-safe**, digital vs physical | Digital **cuts off** (like fail-closed) vs physical **opens up** (protects people) |
| **Fail-soft** vs **fail-open** | Staying **alive** after a component dies vs prioritizing **availability** by letting traffic through |
| **Reference monitor** vs **security kernel** | **Checks** access (the concept) vs the TCB components that **implement** it |
| **Bell–LaPadula** vs **Biba** | Secrecy: no read **up**, no write **down** vs integrity: no read **down**, no write **up** |
| **Simple** vs **star (*)** property | **Simple = read**, **star = write** (in either model) |
| **Biba** vs **Clark–Wilson** | Both integrity: **lattice levels** vs **commercial, subject → program → object** |
| **Trust** vs **assurance** | Mechanisms are **present** vs how **reliable** they are, maintained over time |
| **Confinement** vs **bounds** vs **isolation** | The restriction vs the **limits that enforce it** vs the resulting **separation** |
| **Threat modeling** vs **risk assessment** | **What could go wrong** (enumerate) vs **how much it matters** (prioritize) |
| **Treatment** vs **controls** | **Mitigate/accept/transfer/avoid** (step 5) vs **prevent/bound/recover** (step 7) |
| **Finding** vs **vulnerability** vs **risk** | Scanner output vs a real weakness vs its **significance in context** |
| **SAST** vs **SCA** vs **DAST** vs **pen test** | Code patterns vs **dependency** risks vs **running interface** vs **attack paths** |
| Which verification **proves a requirement** | **Only review + security tests.** Scanners find classes of defect |
| **Authorization** vs **intent** | "Are you allowed?" vs "did you **mean** this?" |
| **Pseudonymized** vs **anonymized** | Reversible, **still personal data** under GDPR vs irreversible, outside the law's scope |
| **GDPR** vs **PDPA** reach | Follows the **data subject** anywhere vs follows **presence in Thailand** |
| **Controller** vs **processor** | Decides **why and how** vs acts **on instructions** |
| **Criminal** vs **commerce** law | **Letter** of the law, prosecutor, punishment vs **intention**, plaintiff, rulings |
| **Copyright** vs **patent** | **Automatic** vs must be granted, and rare for software |
| **GPL** vs **LGPL** | Whole project must be GPL vs only **forks of the library** stay LGPL |
| **Symmetric** vs **asymmetric** | One shared key, fast, **key exchange is the problem** vs keypair, solves exchange, slower |
| **Block** vs **stream** cipher | Fixed blocks (AES), higher security vs continuous stream (RC4), faster |
| **RSA** vs **ECC** | **Factoring** vs **elliptic curve discrete log**; 2048+ vs 256-bit; RSA falls to Shor |
| **Signing** vs **encrypting** | **Private** key signs for authenticity + integrity vs **public** key encrypts for confidentiality |
| **Signature** vs **PKI** | Proves *whoever holds this key* signed vs proves **whose key it is** |
| **Root CA** vs **subordinate CA** | **Self-signed**, pre-trusted vs trusted **because the root vouches** |
| **Legal** vs **ethical** | Parental consent is legally valid and still **ethically insufficient** without child assent |

## 🔑 Ten One-Line Recalls

1. **Security is built in, not bolted on** — design-stage fixes cost 30–60× less, and the objective predates the software.
2. **C-I-A first**: name the pillar before choosing a control. Crypto serves C and I, never A.
3. **Risk = Likelihood × Exposure**, a coarse judgement, not a calculation.
4. **Deny by default, and justify grants** — never justify denials.
5. **Prevention never reaches zero**, so bound the blast radius and plan to recover.
6. **Validation is the gate**: data is trusted only because something checked it at the boundary.
7. **Authorization is not intent**, and `LIMIT 1` is a guardrail, not proof.
8. **A requirement names the principal AND the object**, and comes with a test that can fail.
9. **A scanner finding is evidence, not a risk decision** — only review and security tests prove *your* requirement.
10. **Pseudonymized is still personal data**, quasi-identifiers re-identify people, and small cells leak.
