## 1. Secure Development Lifecycle (SDLC)

Security has to be built into **every stage** of the SDLC; fixing a vulnerability during design costs **30–60x less** than fixing it in production (NIST / IBM / Gartner).

![[ssdlc_loop.png]]

| Stage                | Security Activity                          |
| -------------------- | ------------------------------------------ |
| **Requirements**     | Secure Requirements Review                 |
| **Design**           | Secure Design Review                       |
| **Development**      | Secure Code Review                         |
| **Testing**          | Penetration Testing                        |
| **Deploy/Implement** | Security sign-off                          |
| _(ongoing)_          | **Maintain** — feeds back into every stage |

> **Key principle: be flexible.** The *SDLC is a loop*, not a straight line — findings at any stage can send you back to an earlier one.

## 2. The Four Phases in Detail

### 🔹 Requirements

- Identify key security risks: **data sensitivity**, **functionality**, **use-case modeling**
- Involve group risk / internal audit early to avoid conflict later
- Check applicable **group standards**, legal, and regulatory requirements
- **Decide**: is the project acceptable from a security standpoint, and what controls are required?

### 🔹 Design

Threat modeling — 4 steps:
![[threat_modeling_four_steps.svg|579]]

| Step           | What it means                                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Decompose**  | *Map* the app's parts: data flows, trust boundaries, entry points, sensitive data                                  |
| **Categorize** | *Classify threats* per part (e.g. STRIDE: spoofing, tampering, repudiation, disclosure, DoS, privilege escalation) |
| **Rank**       | Score by *likelihood × exposure* to prioritize                                                                     |
| **Mitigate**   | *Assign a control per threat* (prevent, reduce, or limit damage)                                                   |
**Output**: security **technical specifications** + a **security test plan**.

### 🔹 Development

- Developer security-awareness *training*
- *Unit testing* of security-specific features
- *Code review*:
    - Secure coding standards
    - Automated code-review tools
    - Independent review (3rd party / IT security)

✍️ **Unit testing**: testing the smallest independent pieces of code (individual functions/methods) in isolation, to verify *each* *one* *behaves correctly* on its own before it's combined with the rest of the system.

### 🔹 Testing

- *Verify the design* was implemented correctly
- *Execute the test plans* from the design phase
- Independent *penetration testing* (incl. infrastructure)
- Formal **security sign-off** before production deployment

## 3. Analysis Techniques

| Type                    | Full name                                                  | What it does                                                                      | Notes                                                                                                                                                                          |
| ----------------------- | ---------------------------------------------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Static (SCA / SAST)** | Static Code Analysis / Static Application Security Testing | Scans the source code *before* it's compiled or run                               | Required *checkpoint* before code can leave the SDLC; assures QA the code is ready for testing; can be *wired into the build process* so every automated build triggers a scan |
| **Dynamic (DAST)**      | Dynamic Application Security Testing                       | Tests the *running* application, looking for unexpected behavior at the interface | Can *run multiple times per iteration*; supports *24/7* monitoring; should be tied into the incident response process                                                          |

## 4. Microsoft Secure Development Lifecycle (SDL) — 12 Practices (summarized)

1. **Provide Training** — security is everyone's job
2. **Define Security Requirements** — update continuously as features/threats change
3. **Define Metrics & Compliance Reporting** — set a minimum bar, hold teams to it
4. **Perform Threat Modeling** — find risks, choose mitigations
5. **Establish Design Requirements** — consistent protection guarantees
6. **Define Cryptography Standards** — use vetted libraries, keep them swappable
7. **Manage Third-Party Component Risk** — maintain an inventory, have a patch plan
8. **Use Approved Tools** — publish an approved toolset + required checks
9. **Perform SAST** — analyze source before compilation
10. **Perform DAST** — verify the compiled/running system
11. **Perform Penetration Testing** — simulated attacks by skilled professionals
12. **Establish Incident Response** — a plan ready before something goes wrong

## 5. Where Requirements Come From

Security requirements are **derived**, not invented — from two sources:

**A. Standards, laws & regulations**

- GDPR, PDPA, HIPAA
- ISO/IEC 27000-series
- NIST SP 800
- OWASP ASVS
- PCI Security Standards

**B. Business/product requirements**, split into:

- **Positive** — what the app _must_ do
- **Negative** — what the app _must not_ do

|Positive (functional)|Negative (risk-driven)|
|---|---|
|Lock account after 6 failed logins|Data must not be alterable/destroyed by unauthorized parties|
|Passwords ≥10 alphanumeric chars|App must not be usable for unauthorized financial transactions|
|Mask confidential fields on screen|_(harder to test — no defined "expected" behavior)_|
|Password reset must verify username + email before sending temp password||

## 6. Major Standards, Compared

### ISO/IEC 27000-series

- A **management system standard**, not a technology spec — security isn't achieved through tech alone
- **27000** — vocabulary/overview
- **27001** — requirements to establish/run an ISMS (the certifiable one)
- **27002** — security controls
- **27003** — implementation guidance
- ISO/IEC 27001 requires orgs to: identify risks → design & implement controls → maintain an ongoing management process, with evidence to prove compliance

### NIST SP 800

- Published by the U.S. National Institute of Standards and Technology
- **SP 800-53** = Security & Privacy Controls for Information Systems and Organizations

### OWASP

Non-profit focused on **application** security. Key outputs:

- **OWASP Top 10** — top 10 web app security risks
- **ASVS** — Application Security Verification Standard (web)
- **MASVS** — Mobile ASVS
- Testing Guide, WebGoat (deliberately vulnerable training app)

**ASVS purpose:** give devs a concrete requirements checklist, usable as:

- a **metric** (how trustworthy is this app?)
- **guidance** (how do I build the right controls?)
- a **procurement basis** (what do I demand from a vendor/contract?)

**ASVS Levels**

|Level|For|Verification style|
|---|---|---|
|1|Low assurance apps|Fully pen-testable by a human, black-box, no source needed|
|2|Apps with sensitive data (**recommended default**)|Secure coding, architecture review, SAST/hybrid, unit tests|
|3|High-value transactions, sensitive medical data, max trust needed|Same as L2 but at the highest rigor|

### PCI Security Standards

- Founded 2006 by Amex, Discover, JCB, MasterCard, Visa
- **PCI DSS** — Data Security Standard (12 major requirement areas)
- **PA-DSS** — Payment Application DSS
- Also: PCI Secure Software Lifecycle Requirements, PCI Secure Software Standard

---

## ✅ Key Takeaways

1. **Select** the standards/laws/regulations that apply to your app.
2. **Read and understand** the detailed requirements those standards impose.
3. **Choose controls** to design and implement based on actual risk — not blanket compliance theater.
