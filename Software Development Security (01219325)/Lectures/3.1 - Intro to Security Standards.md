## 2. Risk Assessment

**Formula:** Risk = Likelihood × Exposure (or Impact)
- **Likelihood** = how likely is someone to actually attack this thing?
- **Exposure** = how much damage happens if the attack actually succeeds.
![[risk_table.png]]

| Scenario                                         | Score                               |
| ------------------------------------------------ | ----------------------------------- |
| GPS box exposed on network                       | 2 (low exposure, medium likelihood) |
| Admission system with minimal input verification | 2 (medium likelihood, low exposure) |
| LAN loop in a department                         | 6 (medium/high)                     |
| Registration data leak                           | 6 (high/medium)                     |
| PDPA violations                                  | 6–9 (high/medium-high)              |

**NIOSH example:** a more *complex model can combine several factors* (e.g. transmission rate + vaccination rate + personal contact + transport mode) for finer-grained risk scoring — useful when a simple 2-variable matrix isn't precise enough.

### What drives likelihood vs. exposure

| Likelihood factors                                                               | Exposure factors                                            |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Industry risk** (high: banking, fintech, health; low: general trade)           | **Downtime/disruption** impact (e.g. SLA violations)        |
| Known **incident rate**                                                          | **Legal liability** (civil/criminal, HIPAA, GDPR fines)     |
| Risk of **internal mistake**                                                     | **Reputational** damage, **customer loss**                  |
| Risk of **opportunistic attack**                                                 | **financial** damages                                       |
| Software stack **popularity** (popular = more exploited, even for your own code) | Damage to **employee health/life**, including psychological |

## 3. Balancing Convenience and Security

A system with no connections and no functionality is "perfectly secure", but also useless. Every feature you add expands what needs protecting.

**Example:** a library reservation system starts simple, but adding in-app payments brings in new obligations.

**Core secure design principles**

| Principle                   | Meaning                                            |
| --------------------------- | -------------------------------------------------- |
| **Least privilege**         | Grant *only* the *permissions needed*              |
| **Defense in depth**        | Use *multiple independent controls*                |
| **Secure by default**       | *Default state* should be *safe*                   |
| **Minimize attack surface** | *Remove unnecessary* interfaces/features           |
| **Trust boundaries**        | Treat lower-trust inputs/systems cautiously        |
| **Fail securely**           | *Failure* must *never* *accidentally grant access* |
|                             |                                                    |

**From design decision to coding implementation**

| Design decision              | Coding implementation                  |
| ---------------------------- | -------------------------------------- |
| *Role-based* access model    | Server-side *authorization* checks     |
| *Untrusted input* boundary   | *Validation* + parameterized queries   |
| Sensitive-data requirement   | TLS + hashing + secret management      |
| Limited component privileges | Restricted service/DB accounts         |
| Secure session design        | Secure cookies, token rotation, logout |
| Safe failure behavior        | Generic errors, protected logs         |

## 6. Secure Coding Practices

**Where it fits:** 
![[ssdlc_pipeline.svg|640]]
**Why it matters**: a small bug can escalate: 
![[bug_to_impact_escalation.svg|640]]
### 1. Validate input & prevent injection

Flow: `User/API input → Validate → Use safely`

| Practice                           | Detail                                       |
| ---------------------------------- | -------------------------------------------- |
| Validate *server-side*             | Check type, length, range, format            |
| Prefer *allowlists*                | Define what's acceptable, not every bad case |
| Keep *data separate from commands* | Parameterized queries, safe APIs             |
|                                    |                                              |
**Prevents**: SQL injection, XSS, command injection.

**Example: data must stay data:**
![[secure_query.png]]

### 2. Authentication, authorization & least privilege

| Control         | Question it answers                   |
| --------------- | ------------------------------------- |
| **Authentication**  | Who are you?                          |
| **Authorization**   | What can you do?                      |
| **Least privilege** | How much access do you actually need? |
**Important**: hiding a *UI button* is not the same as enforcing *server-side authorization*.

### 3. Protect sensitive data

| Control                        | What it means                                                                                |
| ------------------------------ | -------------------------------------------------------------------------------------------- |
| **TLS**                        | *Encrypts data* while it *travels between system*s, so no one can read it in transit         |
| **Password hashing & salting** | Store scrambled passwords, never the real ones — so a *leak doesn't expose actual passwords* |
| **Secret management**          | Keep *API keys and credentials* out of your code — store them somewhere secure instead       |
| **Trusted crypto libraries**   | Use well-tested, established *encryption tools* — don't build your own crypto                |
Also watch for outdated hashing algorithms, not just missing ones.

### 4. Sessions, errors & logging

| Area     | Practice                                                           |
| -------- | ------------------------------------------------------------------ |
| **Sessions** | Unpredictable IDs, regenerate after login, timeouts + logout       |
| **Errors**   | Generic user-facing messages, no stack traces, no internal secrets |
| **Logs**     | Record security events, protect log access, never log secrets      |
Never expose: session tokens, passwords, API keys, or DB details.

### 5. Dependencies, configuration & verification

Risk is inherited from: application code → libraries/frameworks → runtime/server → configuration.

| Verification method  | What it checks                 |
| -------------------- | ------------------------------ |
| **Peer review**      | Logic and unsafe API use       |
| **SAST**             | Automated static code analysis |
| **Security testing** | Behavior in a running system   |
| **Monitoring**       | Issues detected after release  |
Tools assist developers — they don't replace security reasoning.

### Developer security checklist

- [ ] **Input** — validated untrusted data?
- [ ] **Queries** — parameterized / safe APIs?
- [ ] **Access** — authorization checked server-side?
- [ ] **Privilege** — only necessary permissions granted?
- [ ] **Secrets** — credentials and keys protected?
- [ ] **Errors** — no sensitive details exposed?
- [ ] **Dependencies** — maintained and patched?
- [ ] **Review** — security-sensitive code verified?

Secure coding is a repeated engineering habit, not a one-time checklist.

## Key Takeaways

- SSDLC bolts a *security* activity onto *every stage* of the normal *SDLC*; it's not a separate process.
- *Risk = Likelihood × Exposure*; both sides have their own driving factors (industry, incident rate, legal liability, reputational damage, etc.).
- Every added feature or convenience expands the attack surface; security and functionality are a constant trade-off.
- *Threat modeling* and *secure design* principles (least privilege, defense in depth, fail securely, etc.) belong in the _design_ phase, before code is written.
- *Secure coding* turns design decisions into concrete controls — input validation, parameterized queries, proper authN/authZ, encrypted secrets, safe sessions/logging, and dependency hygiene.
- A small bug can cascade into a full security incident: *Bug → Vulnerability → Exploit → Impact.*
- ISO 27001 gives the compliance framework; OWASP gives the practical guidance and tooling to satisfy it.
