**Format:** 30 multiple choice. One best answer. Answers at the end.

**1.** Fixing a vulnerability during **design** costs, compared with production (NIST / IBM / Gartner):

- A. About the same
- B. **30–60× less**
- C. 30–60× more
- D. Nothing, if you have DAST

- B. The SDLC is a **loop**, not a straight line — findings at any stage can send you back to an earlier one

- B. **Secure Design Review / Secure Code Review / Penetration Testing**

- D. Training / metrics / incident response only

**5.** **Deploy/Implement** uses **security sign-off**. **Maintain** is:

- A. A one-shot production checklist
- B. **Ongoing** and **feeds back into every stage**

- D. Only PA-DSS

**6.** In **Requirements**, key security risks to identify include:

- A. STRIDE categories only
- B. **Data sensitivity, functionality, use-case modeling**

- A. Replace threat modeling
- B. **Avoid conflict later**
- C. Skip legal and regulatory checks
- D. Make ASVS Level 1 the default

**8.** A Requirements **decide** step is:

- A. Whether SAST ran before compile

**9.** Threat-modeling **Decompose** means:

- A. Classify threats with STRIDE
- B. **Map** the app’s parts: data flows, trust boundaries, entry points, sensitive data

**10.** **Categorize** uses STRIDE, which is:

- A. SAST, DAST, review, inventory, deploy, evaluate

**11.** **Rank** scores threats by:

- A. ASVS level only
- B. **Likelihood × exposure** to prioritize
- C. Lines of code
- D. Whether the app is black-box pentestable

**12.** **Mitigate** means assign a control per threat (**prevent, reduce, or limit damage**). Design-phase **output** is:

- A. Only a training roster
- B. Security **technical specifications** + a **security test plan**
- C. Only an approved toolset
- D. Only PCI PA-DSS

**13.** **Unit testing** in this lecture is:

- A. Testing the running app at the interface (that is DAST)
- B. Testing the **smallest independent pieces** (functions/methods) **in isolation** before combining them
- C. A full independent pentest including infrastructure
- D. Scanning source before it is compiled (that is SAST)

**14.** Development **code review** includes secure coding standards, automated tools, and:

- A. Only UI button hiding
- B. **Independent review** (3rd party / IT security)
- C. Only ISO 27003 guidance
- D. Only MASVS

**15.** Testing must **verify the design was implemented correctly**, **execute the test plans** from design, include independent pentest (incl. infrastructure), and:

- A. Skip sign-off if SAST passed
- B. Get formal **security sign-off** before production deployment
- C. Invent new requirements instead of using standards
- D. Replace incident response

**16.** **SAST / SCA** scans source **before** it is compiled or run. It is a required **checkpoint** before code can leave the SDLC and:

- A. Cannot be wired into the build
- B. Can be **wired into the build** so every automated build triggers a scan
- C. Is the same as pentest by skilled professionals
- D. Only supports 24/7 interface monitoring

**17.** **DAST** tests the **running** application at the interface. It can run **multiple times per iteration**, supports **24/7** monitoring, and should be tied into:

- A. Only requirements review
- B. The **incident response** process
- C. ISO 27000 vocabulary only
- D. Clean-room reverse engineering

**18.** Microsoft SDL practice 1 is **Provide Training** because:

- A. Security is only the pentest vendor’s job
- B. **Security is everyone’s job**

**19.** SDL **Define Cryptography Standards** means use **vetted libraries** and keep them **swappable**. **Manage Third-Party Component Risk** means:

- A. Ignore dependencies if they are popular
- B. Maintain an **inventory** and have a **patch plan**
- C. Only run WebGoat
- D. Skip DAST

**20.** SDL **Perform SAST** = analyze source **before compilation**. **Perform DAST** = verify the **compiled/running** system. **Perform Penetration Testing** = simulated attacks by:

- A. The same unit tests as development
- B. **Skilled professionals**
- C. Only black-box ASVS Level 1 tools
- D. PCI card brands

**21.** SDL practice 12 is **Establish Incident Response**:

- A. After the first breach only
- B. A plan **ready before** something goes wrong
- C. The same as security sign-off
- D. Only metrics and compliance reporting

**22.** Security requirements are **derived, not invented**, from:

- A. Only developer preference
- B. **(A) standards, laws & regulations** and **(B) business/product requirements**
- C. Only STRIDE
- D. Only Microsoft’s 12 practices

**23.** **Positive** requirements are what the app **must** do. **Negative** are what it **must not** do. An example **positive** item is:

- A. Data must not be alterable by unauthorized parties
- B. **Lock account after 6 failed logins**
- C. App must not be usable for unauthorized financial transactions

**24.** Negative requirements are **harder to test** because:

- A. They always have a numeric expected result
- B. There is **no defined “expected” behavior**
- C. They are the same as SAST checkpoints
- D. They replace GDPR and PDPA

**25.** ISO/IEC **27001** is the **certifiable** ISMS **requirements** standard. **27002** is:

- A. Vocabulary/overview (that is 27000)
- B. **Security controls**
- C. Implementation guidance (that is 27003)
- D. NIST SP 800-53

**26.** ISO 27001 is a **management system** standard, not a technology spec. Orgs must identify risks → design & implement controls → maintain an ongoing process, with:

- A. No evidence needed

**27.** **NIST SP 800-53** is:

- A. PCI DSS’s 12 requirement areas

- D. WebGoat

**28.** OWASP **ASVS** is usable as a **metric**, **guidance**, and a **procurement basis**. **Level 2** (apps with sensitive data) is the:

- A. Black-box-only, no source needed level
- B. **Recommended default**
- C. Highest-rigor medical/high-value level only

**29.** ASVS **Level 1** is fully pen-testable **black-box**, no source needed. **Level 3** is for high-value transactions / sensitive medical / max trust, same as L2 but:

- A. Without SAST
- B. At the **highest rigor**
- C. Without architecture review
- D. Founded by Amex, Discover, JCB, MasterCard, Visa

**30.** **PCI DSS** (founded 2006 by those card brands) has **12 major requirement areas**. The lecture’s closing advice: **select** applicable standards, **read** their requirements, and **choose controls** based on:
