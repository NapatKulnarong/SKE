## 1. OWL Ontology: Core Elements

**OWL** = Web Ontology Language

An OWL ontology mainly consists of:

- **Classes**
- **Properties** (relations)
- **Individuals** (instances of classes)
- **Relationships between individuals**

### Class vs. Individual
![[class&Individual.png]]

|Question your ontology must answer|Treat "Golden Retriever" as|
|---|---|
|"What breed is this?"|**Individual** (instance of `DogBreed`)|
|"Tell me about this specific dog"|**Class** (with individual dogs as instances)|

## 2. Properties

**Properties** assert facts — general facts about classes, or specific facts about individuals.

|Type|Connects|Example|
|---|---|---|
|**Object property**|class ↔ class (or individual ↔ individual)|`MadeFrom`: Wine → Grape|
|**Data property**|class ↔ datatype|`yearValue`: VintageYear → integer|

```xml
<owl:ObjectProperty rdf:ID="MadeFrom">
  <rdfs:domain rdf:resource="#Wine" />
  <rdfs:range rdf:resource="#Grape" />
</owl:ObjectProperty>

<owl:DatatypeProperty rdf:ID="yearValue">
  <rdfs:domain rdf:resource="#VintageYear" />
  <rdfs:range rdf:resource="&xsd;positiveInteger"/>
</owl:DatatypeProperty>
```

- **domain** = what the property starts from
- **range** = what the property points to
---
## 3. Property Hierarchy

Like classes, **properties can have sub-properties** (`rdfs:subPropertyOf`).

**Step 1 — basic property:**

```
Food --hasIngredient--> Ingredient
```

**Step 2 — sub-property with its own range:**

```
Food --hasIngredient--> Ingredient
Food --hasSeasoning----> Seasoning      (hasSeasoning ⊂ hasIngredient)
```

**Step 3 — sub-property can also narrow the domain:**

```
Food  --hasIngredient--> Ingredient
Pizza --hasTopping-----> PizzaTopping   (hasTopping ⊂ hasIngredient)
```

Here `Pizza` is a subclass of `Food`, and `PizzaTopping` is a subclass of `Ingredient` — the sub-property narrows _both_ domain and range.

**Key idea:** a sub-property inherits the meaning of its parent property but can restrict domain/range to more specific classes.

## 4. Property of an Individual

**Class-level definition** — what properties can `Country` have?

```
Country --locatedIn----------> Continent
Country --hasCapitalCity-----> City
Country --hasOfficialLanguage-> Language
```

**Individual-level example** — Thailand:

```
Thailand --locatedIn----------> Asia
Thailand --hasCapitalCity-----> Bangkok
Thailand --hasOfficialLanguage-> Thai
```

⚠️ To assign these property values, you must **first create the individuals** (`Asia`, `Bangkok`, `Thai`) before linking them to `Thailand`.

```xml
<City rdf:ID="Bangkok" />
<localName rdf:datatype="&xsd;string">กรุงเทพมหานคร</localName>

<Continent rdf:ID="Asia" />
<Language rdf:ID="Thai">

<Country rdf:ID="Thailand">
  <locatedIn rdf:resource="#Asia"/>
  <hasCapitalCity rdf:resource="#Bangkok" />
  <hasOfficialLanguage rdf:resource="#Thai"/>
</Country>
```

## 5. Broad Classes of Ontologies

Ontologies are typically organized in **three layers**, from most general to most specific:

|Layer|Scope|Examples|
|---|---|---|
|**Upper (Foundational)**|Domain-independent, universal/common-sense concepts|DOLCE, SUMO, OpenCyc, BFO, GFO|
|**Mid-level**|Bridges abstract upper concepts to concrete domain concepts|AIRS, MILO, STATO|
|**Domain**|Concepts specific to one field/application|Gene, Rice, Wine, Disease, Software ontology, MESH|

### Upper Ontology

- Defines basic notions: objects, relations, events, processes
- High-level, **domain-independent**, highly reusable
- Represents _common-sense_ / universal concepts
- **Purpose:** aids semantic integration — ontologies built on the same upper ontology are easier to merge/map
- Example: OpenCyc's top hierarchy (`Thing` → `Individual` / `PartiallyIntangible` → ... → `Relation`, `Predicate`, etc.)

### Mid-Level Ontology

- Bridges the gap between abstract upper concepts and specific domain concepts
- Represents knowledge at an **intermediate** level of detail, independent of a specific task
- Includes commonly reused concepts like **Time** and **Location**

### Domain Ontology

- Specifies concepts for **one specific domain**, from a specific viewpoint
- A **viewpoint** = how a group of users conceptualizes a phenomenon
- Often built by **importing/extending** mid-level or upper ontologies (reuses their semantic richness, eases integration)
- Ontologies built for a **specific task/application** are called **application ontologies**

### Local / Application Ontologies

- A further specialization of a domain ontology
- Reflects **one user/developer's** particular view — no guarantee of consensus or shared understanding

---

## Layer Relationship (Summary)

```
Upper Ontology        (universal concepts: e.g. Object, Event, Relation)
        ↓ extends
Mid-Level Ontology     (intermediate concepts: e.g. Time, Location)
        ↓ extends
Domain Ontology        (field-specific: e.g. Wine, Gene, Disease)
        ↓ specializes
Application Ontology   (single viewpoint, task-specific)
```
